# 用 spec 与证据做 vibe coding

本章是2026-10-12开发流程整理的教学，也可作为后续操作手册。你负责描述问题、判断产品取舍和验收结果；AI负责检查代码、整理必要规格、实现、验证和交接。常规步骤不需要你逐项提醒或批准。

## 1. 为什么改流程

以前的README/PLAN/技术规格经常在顶部追加最新说明，正文保留旧规则。新会话需要解释历史才能知道现在怎样做。现在分成四种材料：长期约定、现行契约、一次变更、实际证据。你的自然语言指令仍优先；文档负责让下一次会话无需重听整个故事。

```text
你的目标或失败例子
        ↓
核对现行规格、代码与工作区
        ↓
一页变更单：预期行为 + 范围 + 验收
        ↓
最小实现 → 适用测试/检查 → 复核diff与结果
        ↓
更新现行契约（有变化才改）+ 教学 + 进度
        ↓
你试用/看证据 → 下一个阶段
```

spec是可检查的约定。比如“2025年数据缺失时保留用户目标并列缺口”，能转成输入/预期；“更智能、更稳定”需要继续拆。spec文件本身不执行，业务规则要由Python契约/校验、提示词和测试分别落实。

| 你或AI要知道的事 | 去哪里读/写 |
| --- | --- |

| 实际做了什么与没证明什么 | [PROGRESS](../PROGRESS.md) + 变更单验证栏 |
| 关键决定的原因 | [decisions](decisions.md) |
| 以前怎么决定/实现的 | docs/history与编号教学章，按需要读 |

现行规格只写当前规则，不写“下面旧值以这段为准”。历史全文已归档，旧测试结果和失败都保留。PROGRESS记录不替代测试，源码也不能独自决定业务需求；发生不一致先报告，再按授权修正。

编号教学章是当时实现的讲解，不要求本次全量改写。查当前规则优先现行规格；需要原因才读历史。以后维护文档也遵守这个分工，不让“文档驱动”变成每次重写全仓。

## 3. 每次开发怎样进行

### 第一步：你给目标或真实失败

通常说清“哪里不好用、希望得到什么”，最好给一份失败输入/输出。无需自己先设计模块或写完整规格。

可直接发：

> 按项目当前开发流程，修复这个问题：……。希望输入……时得到……。本轮只完成这个可独立验收的结果。先核对代码，把预期、范围和验收写进变更单；常规实现自行决定，完成适用验证、中文讲解与交接。

如果只想讨论，直接说“只评审，不实施”。如果产品问题尚模糊，说“先梳理会改变结果的选择”；AI只追问必要选择，可只读查清的事实先检查。

### 第二步：AI按任务大小写规格

| 改动 | 需要的材料 |
| --- | --- |
| 拼写、链接、简单展示文字 | 直接改、检查；不强制新建变更单或业务测试 |
| 明确bug或小功能 | 一页变更单，通常3–5项验收 |
| 数据迁移、授权、预算、架构 | 变更单加必要设计、失败/兼容方案，按可运行结果分阶段 |

用户已经授权明确行为，就不再等你批准一遍同样的方案。规格内的工程默认值可自行实施；改变研究方法、范围、外部权限或真实费用额度的未决点需要你决定。

验收先于实现。能用“给定条件 → 执行动作 → 看到结果”写清即可，不强迫所有需求套形式。复杂设计可以先做明确标为临时的隔离探索，不能把探索结果直接当正式契约或冻结报告。

### 第三步：修机制，验证用户结果

例如“年份与值配反”：先保存失败证据，要求期间/值/单位/来源作为同一事实，再测试打乱排序、缺年和另一指标。不要要求“写一个名为fix_roe的函数”，也不要按腾讯或题号分支。

代码、测试、提示词/项目Skill都可能是实现；Skill指导模型，Python控制权限和数值规则。离线脚本模型按预设路线走通，不等于真实模型会选这条路线。必要时增加真实评测，不能靠增加文档或预算代替验证。

### 第四步：检查、审阅、交接

AI先跑适用检查，再对照每项验收看diff和结果。自我复核不是独立评审；高影响改动可由你另开只读review或请其他审阅者检查，不能凭空声称独立审查通过。

结尾应给：改了什么、为什么、实际验证、未验证/限制、一个试用例子。所有适用标准满足才完成；工程通过而真实效果未知，明确保留“真实质量待验证”。教学阶段完成后暂停，你决定下一阶段。

## 4. 现在可用的本地自动化

实现文件是 [scripts/dev_check.py](../scripts/dev_check.py)，仅标准库编排已安装的Git/Ruff/pytest/npm。无需安装Spec Kit/OpenSpec/Kiro，也没有新增运行时Agent或软件后台。

在项目根运行；平时也可直接让AI替你执行：

```bash
# 新会话只读摘要：当前入口、10项源码默认值、工作区、变更单路径
./.venv/bin/python scripts/dev_check.py context

# 文档/规格改动：现行入口围栏/相对链接、默认值、历史哈希、diff、Ruff
./.venv/bin/python scripts/dev_check.py check

# 代码小改：加相关行为测试；此处用本次工具的真实测试文件
./.venv/bin/python scripts/dev_check.py check --tests tests/test_dev_check.py

# 跨模块变化：完整离线测试
./.venv/bin/python scripts/dev_check.py check --full

# 影响两种问答运行时的共用规则时，再检查Pi默认路径
./.venv/bin/python scripts/dev_check.py check --full --pi

# 仅涉及Pi TS/生成文件时，额外运行现有本地npm检查
./.venv/bin/python scripts/dev_check.py check --node
```

stdout返回JSON，进度到stderr；实际报告与子命令日志在 `data/dev-checks/<时间-ID>/`。失败返回非零，缺工具/超时明确失败，不自动安装或把未运行标成通过。默认快速检查没有pytest，报告会列清实际执行项。

默认值检查从AST提取新问题4项限额、两库schema、Writer次数、SQL/函数次数和财报期数，对照技术规格表的10行；不执行业务模块。新增未覆盖的常量/规则需人工复核或按需要扩展，不保证自动找出所有自然语言矛盾。

文档检查只覆盖现行入口、模板与变更单的围栏和内联相对链接存在性，不验证远端链接、所有Markdown语法/锚点或历史章的当前性。档案哈希能发现快照意外改变，不能证明历史业务结论正确。

脚本不读.env/业务库、不运行ask/collect/评测、不打印环境；子进程不继承模型/观测凭据。离线约束仍依赖项目测试正确使用fake，不是OS级网络隔离器。`--node`复用现有tsc检查，会产生它已有的本地构建中间文件，不安装依赖。

## 5. 你的研究Agent应怎样验收

开发检查和研究评测是两条线。问答质量采用：固定输入与来源版本 → 明确允许澄清 → 同runtime/预算运行 → Python独立核对数值/引用 → 人工抽查解释与证据支持。

| 指标 | 检查什么 |
| --- | --- |
| 执行 | 是否结束、等待、失败；如何恢复 |
| 正确性 | 年份/财历、值、单位/倍率、公式、引用身份与实际支持 |
| 缺口 | 是否先查询可用资料、是否诚实说明，缺口不伪装答案 |
| 成本/效率 | tokens、真实调用次数、工具次数、耗时 |
| 泛化 | 未参与修复的公司/指标、边界问题有没有退化 |

原五题可作修复回归，保留未见题检查泛化。真实模型不确定时需适当重复并记录每次，而不是只挑最好一次。费用许可、次数账本与token预算分别处理；此次开发流程整理没有重置原40次或新增真实额度。

## 6. 还有哪些自动化空间

| 事项 | 当前状态 | 下一步价值与条件 |
| --- | --- | --- |
| 新会话交接、默认值/文档检查、命令留证 | 本次已实现 | 让AI按AGENTS自动执行适用检查，你不必反复复制长提示 |
| 一页任务的验收追踪 | 模板/流程已落地，由AI维护 | 先实际用几次，再判断是否值得加生成命令；不要先做任务管理框架 |
| 真实评测准备/执行/结果评分统一入口 | 已有eval_pi_agent执行器与人工审阅，统一入口待做 | 冻结来源与评分；prepare可只读自动化，执行须已有明确预算；不接入默认检查 |
| 数字/单位/引用的确定性评测 | 业务已有部分校验，统一评测汇总待做 | 从当前五题和未见题起步，主观解释仍需人工校准 |
| Git检查点与只读review | Git已存在，本次未提交 | 一阶段一可审阅提交，由你明确授权；现有工作区需先按功能整理 |
| CI/Git hook | 按此前决定继续暂缓 | 需要时复用同一check命令，避免本地/CI两套标准；不做真实接口调用 |

目前优先把五题修复验证闭环做好，再优化SQL/快照性能。没有可观察收益时，不增加新Agent、向量库、编排层、定时任务或更多重复规则。

## 7. 参考了什么，如何适配

资料核对日期：2026-10-12。“最先进”没有统一排名，本流程选择适合已有个人Python项目、能降低维护成本的部分。

- [GitHub Spec Kit](https://github.github.com/spec-kit/)：先定义需求，再规划/拆任务、实现与收口；本项目按改动大小压缩为一页，未安装其CLI/扩展。
- [OpenSpec overview](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md)：现行规格与变更分开，完成后将变更并回正文并保留历史；本项目沿用已有目录和文件名。
- [Kiro Specs](https://kiro.dev/docs/specs/)：区分需求、设计、任务，也提供快速路径；本项目小修复不机械生成三份文件。
- [OpenAI官方最佳实践](https://learn.chatgpt.com/guides/best-practices) 与 [AGENTS指令](https://learn.chatgpt.com/docs/agent-configuration/agents-md)：简洁可执行的项目说明、清晰完成标准及测试/审阅；项目规则已接入根AGENTS。
- [Anthropic Agent评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：执行轨迹与最终结果分开，按验证对象组合确定性、模型和人工评价；本项目优先确定性核对加人工语义抽样，未新增付费judge。

这是对方法的适配，不复制上游实现，不宣称已证明准确率或节省token。实际文件与命令结果见 [本次变更单](changes/20261012-spec-workflow.md) 与 [进度](../PROGRESS.md)。
