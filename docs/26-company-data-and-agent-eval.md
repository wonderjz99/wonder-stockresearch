## 1. 目前有公司数据库吗

**有本地公司资料存储，但还没有持久化、统一可查询的公司事实表。** 当前不是每家公司一个数据库，而是共用一个 `wonder.db`，以 ticker 区分，原文保存在 `data/stocks/<ticker>/`。

| 层次 | 实际内容 | 当前查询方式 |
| --- | --- | --- |
| stocks | ticker、名称、手动清单标记 | SQLite 查询；7 条中 4 条名称为空，但对应 profile 文件有公司名称 |
| sources / run_sources | 来源身份、ticker、数据集、时间、哈希、文件路径、研究关联 | SQLite 筛选来源，读取归档 JSON/PDF/文本 |
| provider JSON | profile、报表/关键指标、经营效率、营收构成、高管、股东、分红等 | 按来源读原文；不同数据集的数值解析覆盖不一致 |
| QueryWorkspace | 从已选归档解析出的 financial_facts、source_metadata | 每次 SQL 构建隔离快照，再执行只读 SQL；主库没有 financial_facts 表 |
| 报告、Memo、Memory | 已完成研究、用户保存观察及检索投影 | 用来定位和理解历史，不替代原始财务事实 |

代码依据：`storage.py` 的 stocks/sources/run_sources，`fixed_quality._numeric_inputs()`，`query_workspace._snapshot_payload()` / `_prepare_sql_run()`，`agent._resolve_context_run()`，`agent_data.fetch_financial_data()`。

当前默认交互上下文会优先选择最新 completed run，找不到才选最新 run；因此公司所有归档中的最新资料，不一定就是当前 Agent 可见的资料。`context=latest_run` 能选择最新 run，但它也不等于跨所有 run 的最新公司资料视图。`context=sources` 当前仍会解析到最新 run，不能把这个名称当作已有跨研究公司数据查询能力。

最新按需补取属于当前 Turn，同一 Turn 可复用，其他 Turn 不隐式混用。这个隔离保证研究范围，但也意味着还没有跨会话共享的、带新鲜度判断的公司数据缓存。

目前按需工具只允许 statements、operational_efficiency、revenue_breakdown 三类财务数据；profile 虽已归档，还没有交互式按需补取入口。基本信息查询与刷新也应纳入下一步公司数据层。

## 3. 怎样使用题集

完整机器可读定义在 [interactive-agent-30.v1.json](evals/interactive-agent-30.v1.json)，包含题号、ticker、问题、入口、条件和验收要点。已为本机生成 `data/evals/manual-30/inputs/Q01.json` 至 `Q30.json`，均经过现有 Pydantic 输入模型校验；没有执行这些问题，没有预填通过结果。

先用 ask 测核心 Agent，再可选用同样文字测试 chat 的路由。ask 样例：

```bash
uv run wonder-research --root . ask HK.00941 --input data/evals/manual-30/inputs/Q11.json
```

默认题目采用 `context=latest_run`，最多六轮、30,000 总 tokens，允许获准的富途资料补取。Q25 明确 allow_network=false，仅禁止资料补取，DeepSeek 请求仍需网络。Q29 要使用 Q11 返回的 session_id 执行 ask-followup，产生新 Turn；不要把所有题目塞进同一个 session。Q30 只通过 ask 检查写入边界，不用它启动正式研究。

数据缺口、季度覆盖、历史时点与写入拒绝也是测试目标，不能以“30 题全部输出数字”为合格标准。原文有指标而解析器查不到，应记为覆盖失败，不能用一句“未披露”掩盖实现缺口。

建议每题记录：数据快照/run_id、Skill/工具版本、session_id/turn_id、结果状态、答案是否正确、是否真正执行计算、引用是否匹配、期间/币种/单位是否正确、补取是否必要、是否重复调用、token、耗时、错误码与备注。结果保存到 `data/evals/<测试批次>/`。涉及计算的题目独立复算，不能只用另一个 LLM 判分。固定年度题优先绑定同一个隔离数据副本；实时补取另分一组，避免数据变化污染前后比较。

## 4. 分阶段计划（A 已完成，其余待实施）

1. **先建立可比较的现状基线。** 用这 30 题定位失败属于数据不存在、解析未覆盖、检索选错、计算未执行、引用或预算。先留存同一数据快照，不边改边覆盖测试结果。当前只交付题集和条件，没有自动执行器或批量真实 API 运行。
2. **独立公司数据层 A 已完成。** 所有公司共用 `data/company.db`，保存可重建的基本信息字段和财务事实投影；`wonder.db` 保留来源登记、研究与会话。已离线解析四类归档、提供人工字段/事实查询、增量导入和重建，并补齐新库备份。固定研究和 Agent 共享新查询层仍属于下一阶段。设计与分阶段状态见 [独立公司数据库计划](27-company-database-plan.md)。
3. **建立明确的数据选择与刷新契约。** 普通交互可选当前公司资料，历史问题按当时已披露范围筛选，正式研究继续限定 run/as_of。字段保留原始键、数值文本、期间类型/起止、币种/单位、会计范围/准则、披露/获取时间、source_id/locator；元数据未知就标未知。相同经济指标的多来源事实并存，不用一个唯一键抹掉冲突。补取后更新可重建投影，新 Turn 可在明确的数据选择与证据回执下复用；缺期间或需要更新时再请求富途。模型 SQL 仍只访问隔离导出的快照。
4. **以相同 30 题复测并收口计算与引用。** 数值衍生结论应关联实际计算产物和输入引用，阻止“文字里算了但无执行记录”。补齐原文阅读回执、年度/季度与累计期间、重复来源和财年解释。建议验收：引用/期间/币种/单位的硬错误为零，禁止写入边界全部通过；有完整原始数据的计算题必须实际执行。正确缺口与正确拒绝单独计分，不算作数值回答成功。
5. **随后优化检索、体积和代码组织。** 修正中文别名与相关片段检索、Turn 工作目标和增量记忆索引；共享重复原文的页索引；补齐计算产物备份与按引用的清理预览。最后再拆工具分发、数据库 SQL 和模型 HTTP 的混合职责，用同一基线证明重构行为不变。继续保持 Python/CLI/SQLite、一个交互 Agent，无需先引入向量库、ORM 或新运行框架。

公司事实投影是原始资料的可重建查询层，不是自动从聊天提炼事实的“长期记忆”，也不改变正式报告冻结规则。完整语义事实记忆仍按原计划后置。每一步独立交付、验证和讲解后暂停；19D.2 包装材料与 GitHub Actions 继续暂缓。
