## 2. 最严重的例子：数值算对，年份写错

Q20 原始归档、SQL 输入的对应关系为：

| 年份 | 归档/SQL 数值 | 最终回答数值 |
| --- | --- | --- |
| 2021/FY | 62.146776 | 58.227439 |
| 2022/FY | 59.784329 | 58.436007 |
| 2023/FY | 59.209519 | 59.209519 |
| 2024/FY | 58.436007 | 59.784329 |
| 2025/FY | 58.227439 | 62.146776 |

实际成功函数先提取数值，再 `sorted`，返回 `values` 数组，没有把每项的 period/fact_id 一起返回。统计计算不受排序影响，模型却把升序数值配到升序年份，使下降序列变成上升序列。

用 Decimal 对原始五个数复算：均值 59.560814，极差 3.919337，总体标准差约 1.4073838336，与函数返回的六位小数一致。因此此处主要问题是计算输出到报告的身份丢失，不是标准差公式错误。

核验来源 `276a4a3f-43bf-464f-b3b8-1645650bbffc` 与 `c25c1f11-dedb-49ae-8877-1bb8b08f5ee2` 的原始文件哈希均匹配登记；只核验归档内字段和值，不证明供应商数值在会计意义上完全准确。

## 3. 其他共性问题与原因

### 3.1 工具语法错误被误写成缺少计算能力

R01/Q11 的事件为 `analysis_function_not_allowed`，节点是 Call，`executed=false`，每题各三次。属于运行前语法拒绝，不能说真实计算运行三次失败，也不能从该错误推出平均值不可计算。现有 12 个允许函数包含 sum/len/float，通用均值函数已经通过本次离线语法探针。

本地 legacy 没有这些 Turn 的 agent_messages，拒绝的函数代码也未归档；本次能确认错误类别/位置，不能确认被拒调用究竟是什么，更不能把它直接归因为旧 Lambda 问题。

更直接的实现问题是：`legacy_agent.execute()` 在收尾时用空工具集合重建 prompt；`agent_policy.build_system_prompt()` 把空集合解释为“当前工具集合不含可信计算能力”。模型因此容易将“本轮停止调用工具”写成“系统不能计算”。两者必须分别表达。

### 3.2 单位依赖模型自行填写

Q20 输入 unit/scale 为 null，正文仍给出百分点，并把毛利率水平也称为百分点。用户要求某种单位，不是数据单位的证据。Q11 本轮正确保留了未知单位，说明单靠提示词的效果不稳定。

### 3.3 时间选择与趋势判断没有程序约束

R01 查询已经取得 2025/FY，主回答仍取 2021–2024。备用序列里 2024/FY 为 21.565778，2025/FY 为 21.375767，原值差为 -0.190011，正文却说连续两年回升。

“近 N 年”应根据来源实际已报告完整年度、财年、时点和覆盖选择，并展示依据。不能用当前年份减 N 猜日期，不能把获取时间、期末或 FY 标签自动当作披露日期。当前归档的披露/审计元数据不足，不能在复盘中替模型补证据。

### 3.3.1 相对时间表达需要明确的解释和追问门槛

用户补充：2026 年问“近三年 ROE”，预期 2023、2024、2025，Agent 却可能选 2022、2023、2024，并未追问。这不能仅凭一次输出归因为模型训练缺陷；当前工程规则也不完整。初始上下文没有专门的本次分析日期/相对期间解释对象；已有 ask_user→waiting_user→respond 通道，但何时必须澄清仍主要由模型决定。

通用方案如下，不给任何公司写死年份：

1. 提供明确的分析基准日期（用户 as_of 优先，否则当前日期，时区明确）、公司财年信息，以及本次来源覆盖/完整年度/披露可用性。当前时间在 Python 中确定，不从模型训练记忆推测；期末/抓取日期仍不冒充披露日期。
2. 将“近 N 年/今年/去年/过去十二个月/截至某日”等解释为结构化期间要求，分清完整财年、自然年、滚动区间、是否含当年未完成期间。分别保存用户目标期间、实际数据期间和确认状态，不能用现有库的最新三条偷偷替换目标。
3. 用户明确写年份则直接按指定范围；本会话已确认且当前适用的口径可复用。首次表达存在多个合理解释、财年不同、最新完整年度或披露状态不明、资料覆盖落后于目标时，必须通过现有 ask_user 先列明确候选年份并暂停，不能只在最终 gaps 中说“需要确认”。例如“你指 2023–2025 三个完整财年吗？当前归档只到 2024；是否接受 2022–2024，还是先补齐 2025？”不能把“只到2024”写成最新完整财年已确定为2024。
4. 若用户目标/已确认规则指向最近三个已披露完整财年，且已证实2025完整财年可用，则程序选择2023–2025，并明示采用范围；不重复询问同一已确认事项。2025未披露或财年非十二月结束时，不能机械套2023–2025。
5. 确认结果追加保存到当前 Turn 工作状态，ask-respond/恢复沿用原预算和来源权限，不覆盖原问题/旧报告。新问题重新判断口径是否适用；最终数字区块核对所选期间与已确认目标完全一致。
6. 离线固定时钟，覆盖跨年、财年非十二月、最新年度已/未披露、仅旧归档、年度/中期混合、用户明确年份、一次确认后续用、等待用户后恢复和批处理 waiting_user。批处理显示待确认状态与恢复入口，不自行选择。时间歧义追问与可由明确 ticker 消除的选股等待是不同问题。

### 3.3.2 Prompt 与函数怎样分工，RAG/复核模型放在哪里（设计补充，未实施）

用户进一步询问是否在函数中硬编码“近3年”、仅改 prompt，或采用 RAG/另一个 sub-agent。当前推荐单 Agent 加结构化任务要求、通用期间解析/校验与明确追问门槛；不在本轮新增模型组件或改变单 Agent 范围。

- **Prompt/现有模型调用**负责理解自然语言，提出指标、原始时间表达、数量、期间单位、完整财年/自然年/滚动区间的候选含义，并标记原文明确指定和模型推测。可加入“近三年/过去三年/最近三个财年/截至某日”等多样示例，但不将某种猜测自动升级为用户已确认。不以模型自报 confidence 或 requires_confirmation 为唯一执行依据。优先扩展现有决策/工具参数，不预设每个问题新增一个独立模型调用。
- **Python 上下文与普通函数**负责提供真实基准日期、来源/财年覆盖、验证 Pydantic 结构、依据明确的期间规则选择具体年份、检查完整性与授权，并把用户确认/未确认状态持久化。可以实现有限的语法辅助解析，但不写“遇到近3年就返回2023–2025”的规则，也不靠正则穷举所有自然语言。函数消费通用的 count、period_basis、as_of、include_incomplete、明确年份等参数；未知语义保留 unresolved。
- **追问条件**由程序检查必需条件决定，例如 relative 期间缺基准或口径、财年/披露状态不明、目标年份与可得年份冲突、候选含义实质不同，返回 needs_clarification 并调用现有等待用户机制。模型可以把候选写得易懂，但不能自行解除等待。明确年份或已确认且仍适用的口径不重复追问。形式校验仍不能彻底证明模型理解原文正确，需原文对应、跨表述评测及必要用户确认。
- **任务要求与覆盖分开**：先记录想查哪些指标/期间/计算/单位，再查到可得事实，最后核对交付是否满足。当前归档只到2024只能改变覆盖状态，不能悄悄改用户目标。最终数字/期间核对共享这份要求；检索与解释阶段可以继续由同一个 Agent 灵活选择工具。
- **RAG/检索**用于取得财年定义、已披露年份、指标口径和引用依据。[RAG原论文](https://arxiv.org/abs/2005.11401)研究的是用检索的外部知识辅助生成。就本项目而言，已有公司事实SQL和归档检索可以提供相关依据，不必为了“近三年”新增向量数据库。检索本身不能决定用户究竟想要完整财年还是滚动36个月，也不能代替确认和确定性期间校验；这属于本项目设计判断。
- **可选复核模型**将来可对照用户原话、已确认任务要求、来源/计算产物及草稿，发现遗漏假设、文字与数字冲突或无证据的因果解释。可以先考虑一次受控只读检查调用，不必直接建立可自主多轮工具执行的 sub-agent。[Anthropic的 evaluator-optimizer 说明](https://www.anthropic.com/engineering/building-effective-agents)强调明确评价标准及可测改进。复核模型的意见仍需证据，不能当作真实年份/正确答案的权威；两个模型可能接受同一未确认假设，增加调用也增加成本/延迟。是否引入须先用相同题集证明增益，并另行明确产品范围/额度；当前不实施。

优先把“理解出的要求 → 必要确认 → 执行 → 对照要求验收”做清楚，再依据残余错误决定是否增强检索或添加语义复核。期间、数值配对、单位和引用等可机械核对的部分先由程序检查，开放语言解释的正确性则不能被结构合格替代。

### 3.3.3 小型问题澄清 Skill：每题检查，按需追问（设计补充，未实施）

用户建议借鉴 grillme 的思路，增加一个小 Skill，让 Agent 先确定用户在问什么。建议纳入 G2，拟名 `question-clarification`，作为同一个交互 Agent 的简短方法 Skill；借用检查假设、发现歧义的做法，不照搬长时间连续盘问，也不新增独立 Agent。

1. **每题检查的清单**：研究对象是否确定；用户要查的指标/口径；明确或相对期间；要列值、算变化、比较还是解释原因；会实质影响结果的公式、单位或范围。按任务需要检查，不把全部字段都设成所有问题的必填项。“可能有用”不等于“必须先问”，用户明确给出的要求优先于会话默认值。
2. **只问影响答案的未知项**：明确“某公司2023–2025年度ROE，列值并计算逐年变化”就直接执行；“近三年”存在多个合理期间且本会话未确认时，列出具体年份候选后问一次。差异不会改变结果的表达无需追问。多个相关缺口合成一个简短问题，给可理解的选项，避免逐项盘问。不能把默认推荐选项当作用户已确认。
3. **先区分意图歧义与资料未知**：财年结束日、归档覆盖、原始单位等可从授权资料查证的事实，先做必要的只读元数据查询，不把资料调查转交用户。若查证后仍存在会改变目标的选择，或需要用户同意改用旧年份/其他口径，才进入 ask_user 等待；用户同意某单位也不能替代来源的单位证据。没有资料且用户没有授权补取时，诚实保留缺口，不循环追问公司事实。
4. **Skill 与程序共用一份任务记录**：Skill 指导现有模型提出简短任务要求、原文依据、已确认项和待确认项；Python 校验结构、提供日期/覆盖，并判断已知必要条件是否满足。状态至少区分 ready、needs_clarification 与超出支持范围；有未解决的必要选择时，允许查询澄清所需资料，但不进入依赖该选择的计算和最终报告接收。模型自称“理解了”不能解除等待。Skill 本质仍是提示词，程序也无法机械证明所有自然语言含义，须保留语义质量评测。
5. **接入共用执行入口**：当前 chat 的 `_load_execution_skills` 会加载所选 Skill，而直接 ask 默认 `skill_context` 为空；不能仅新增文件、只让 Router 偶尔选中。为开放问答明确最小共用方法上下文，覆盖 ask/chat、legacy/Pi、新问题/追问，并沿用 Registry 的版本/哈希审计和 Turn 冻结规则。确认结果写入当前 Turn 的可恢复工作记录；ask-respond、重试、重启恢复沿用原预算、权限与有效确认。新问题要求变化时重新检查，旧报告和冻结的 Skill 记录不回写。方法 Skill 不声明新工具或授予权限。
6. **控制成本与打扰**：检查尽量并入现有模型决策，不预设每题额外调用分类器或复核模型；清单保持短小，实际追问才向用户展示候选与原因。明确的问题无需额外确认轮。验收同时统计“该问却没问”和“本来明确却反复问”，不能以追问次数越多越好。

离线验收覆盖：明确年份直接执行；未确认的相对期间；已有确认复用；用户在追问中修改范围；同名指标不同口径；缺最新年但不得默默替换；无需用户回答的元数据查证；简单问题不被过度盘问；等待后恢复不重置预算；ask/chat 和两种 runtime 行为一致。通用规则按缺失条件与歧义类型处理，不按公司名、题号或完整问题匹配。

### 3.4 检索把名字不同误当作没有数据

Q08 搜“总资产/总负债”，归档实际标签包括“资产合计/负债合计”；现金存在“现金及等价物”和“现金及现金等价物期末余额”等候选。当前仅做有限别名/子串检索，可能先命中周转率、同比和构成比例。

事件显示多次改词序/分页仍回到近似目录，最后还使用目录未返回的 field_key。目录有字段名不代表已读取数值；取不到匹配词不代表公司没披露。上述候选也不能未经口径核实直接合并。

### 3.5 引用只查存在性，不能证明文字内容正确

Q08 把“字段目录检索……无数值”写作 locator，这不是原文位置，当前拒绝正确。另一方面，Q20 的真实 source_id/locator 能通过校验，但不能自动证明“这个数属于这个年份”。[accept_answer](../src/wonder_stockresearch/interactive/agent_execution.py) 当前核对引用资格与回执，没有把正文中的每个年份/数值绑定到具体事实/计算。

legacy 也没有 Pi 的同等有界最终引用修复路径。错误纠正需统一契约，不能通过放宽 locator 校验获得更多 completed。

### 3.6 覆盖缺口没有及时变成停止条件

Q23 当前 statements 批次只包含 annual，季度查询为零符合该来源覆盖。但 Agent 三次查 schema、三次执行相近的零行 SQL，直到十轮收尾。结论应限定为“本次授权归档未取得季度事实”，不能说供应商不支持或公司未披露；没有开启补取，不应联网填空。

## 4. 通用修改原则

所有业务分支以数据类型、期间、指标口径、来源状态、计算操作和错误类型为条件，不以 ticker、公司名、题号或题目原文为条件。五题只作为回归样例，不能成为计算器的路由规则。

通用链路拟改为：

```text
用户问题 → 已验证的指标/期间选择
         → 带 fact_id、period、value、单位和来源的输入行
         → SQL 或受限函数 → 带输入身份的计算产物
         → 程序核对身份/单位/公式结果 → 渲染数值与趋势
         → 模型补充解释；原因证据不足时保留缺口
```

保留 Python/CLI/SQLite、单 Agent、受限 SQL/函数与本 Turn 引用边界。不开放 import、文件、网络、任意方法调用，不增加一家公司一个计算工具，也不把每种财务指标做成固定专用工具。

## 5. 分阶段实施与验收（均待实施）

### G1：受限计算的可纠正错误与真实能力状态

- 在现有 validator/ToolFailure 中返回受控的被拒调用名称/表达式类别、行列、允许用法及最小替代提示；失败代码只在项目 data 下按现有安全边界保留必要诊断/哈希，不记录秘密、隐藏推理或完整模型请求。
- 根据实际授权说明可用的 SQL/函数；将“获准能力”“当前可调用状态”“本次计算成功与否”分开。收尾说明停止原因和未完成步骤，不声称整个系统没有计算器。
- 筛选、排序、期间选取优先 SQL，基础聚合也可用 SQL；确需复杂计算时继续用通用受限 analyze(rows)。给模型与工具契约同源的可运行范式，而非按问题补特例。
- 保留有界恢复/预算与成功 analysis_id，不默认增加轮数。针对错误类型选择修改写法或改用已授权 SQL；最终答案格式/引用错误获得预算内一次具体修复反馈，不能重跑成功采集或放宽回执。
- 验收：不同公司/随机数值下均值、总和、差值、极差、标准差成功；语法拒绝→纠正；收尾不误称无能力；legacy/Pi 的预算、授权和最终引用修复一致。

### G2：计算产物到报告的身份、单位、时间与趋势

- 增加3.3.3的小型问题澄清方法 Skill，与共用的结构化任务要求/程序检查配合；每题检查但仅必要时追问。覆盖直接 ask、chat、两种 runtime 与确认后恢复，不能只依赖 Router 选择；同时验收漏问与多问。
- 输入行保留 fact_id、字段/口径、period、value、unit/scale/currency 和来源回执。排序携带整行身份；为统计临时提取数值时，返回的排序数组不得自动用作逐年表。
- 定义可验证的数值区块：直接事实引用 fact_id；派生结果引用 analysis_id、具体结果键、输入 fact_id 集合及操作/公式。模型不能自写一个 ID 就获得信任，程序须核对归属、输入覆盖与实际结果。
- 逐年表由原始/验证后的行渲染；统计值来自成功产物；精度和显示舍入分开。自由文字里重复数字的策略必须同步收紧，否则仅加数值表不能阻止正文写错。
- 单位根据可追溯的供应商/原始定义做版本化映射，保留未知。不从指标名、数值大小或用户目标单位猜倍率；百分比水平与百分点差区分，金额/币种、倍数同样处理。未知单位允许满足可比性条件的原值运算，但结果只能保留原始尺度并说明限制。
- “近 N 个完整年度”按已确认的期间/范围选择；年度、中期、季度与时点不混用，重复/修订按来源版本规则处理。缺披露或可用性元数据时标记不确定，不伪造已报告证据。 相对时间解释及必须追问规则见3.3.1：基准日期由程序提供，目标期间与可得期间分开，有歧义先等待用户确认，不能把确认留到最终报告之后。
- 上升/下降/持平等数值趋势由排序后的相邻差值产生；对“明显”“趋稳”等程度词设透明依据或避免输出，经营原因仍须独立证据。
- 验收：打乱行序、按值排序、倒序年份、负数/零值、同名不同口径、缺单位、倍率差异、多币种、缺年/修订、非十二月财年。逐年表与输入一一对应，任意重排不改变对应；增加未用于开发的指标/公司验证通用性。

### G3：字段检索、覆盖诊断与没有进展的循环

- 检索扩展使用供应商/指标别名候选，先匹配完整指标，再区分原值、同比、比例和组成项；别名只生成候选，不直接证明可合并。多指标问题拆成可核验字段选择，禁止猜未返回的 field_key。
- 工具区分字段目录、实际事实、计算结果与查询范围/零行观察；分别给可引用事实 ID 和非事实诊断引用。目录说明不能冒充原文 locator，零行结论只覆盖真实执行的范围。
- 紧凑目录的分页与模型实际可见投影保持一致；工作清单记录“已看到的字段/已取得的值/缺的期间”。不能把完整业务结果已返回误当作模型已读完。
- 对等价条件、同快照和重复零结果识别无新增信息；不同分页/范围的合理检索继续允许。未覆盖的季度等场景返回类型/期间覆盖摘要，提出下一种有效查法或有依据地收尾，不循环换词。
- 保留 D2 SQL 筛选下推/快照复用，但性能优化必须在结果/引用一致的前提下测量。D1 人工展开视图仍保留在计划，排在主要正确性修复之后。
- 验收：不同供应商标签、合计/总计、金额与比例易混淆、同义词、多条件分页、目录截断、仅年度无季度、解析失败/未采集等。核对检索次数、实际可见记录和覆盖解释；不承诺固定提速比例。

### G4：分清“程序完成”和“任务答对”

- 不改历史 completed 记录或覆盖旧报告；新增质量验收维度：数据覆盖、期间/口径、计算执行、身份对应、单位、引用、趋势、缺口是否正确。
- 离线先用虚构且变化的公司/指标/数据，做独立 Decimal 复算及身份/单位测试；再验证 legacy/Pi。原五题与未见题共同验收，不能只背住这五题。
- 后续真实复测固定数据快照、runtime、入口、Skill、模型、预算和权限；变更因素分别记录。真实执行需明确额度，不自动重置原 Pi 40/40 账本，不静默发起新问题。

实施顺序建议为 G1 → G2 → G3 → G4，按一个可独立验收的教学阶段完成代码/测试/讲解后暂停；不将所有阶段一口气合并，也不在本复盘轮修改业务实现。
