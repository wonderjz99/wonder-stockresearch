# 独立公司数据库计划

> 本文保留阶段设计与讲解；截至2026-10-12的现行契约以[技术规格](technical-spec.md)为准，当前待办/实际状态见[PLAN](../PLAN.md)与[PROGRESS](../PROGRESS.md)，不以旧阶段限制覆盖当前规则。

2026-10-08，设计与分阶段计划；2026-10-11 补充查询与存储优化待办。A 阶段独立公司库、离线解析和回填已完成，详见 [实现与验证](28-company-data-store.md)；B 共享查询已完成，详见 [B 实现和冒烟质量限制](29-company-agent-query.md)，C、D 尚未完成。用户提出将公司的基本信息、财务等数据放入单独数据库。本计划修订此前“在 wonder.db 内增加事实投影”的建议；保留 Python、sqlite3、CLI 与归档证据，不增加数据库服务。

## 1. 建议与依据

建议增加 **`data/company.db`，所有公司共用，以 ticker 区分**。`wonder.db` 继续保存研究、会话和来源登记。公司资料跨研究复用，具体研究与 Turn 固定自己使用的来源版本。

实际盘点发现七家公司已有基本资料和财务归档，但主库没有持久 financial_facts，查询仍逐次解析并生成隔离快照；经营效率与营收构成的 14 个最新非空原文目前都没有被解析出数值。因此重点是结构化覆盖、来源版本和数据选择，单独新建一个空数据库无法解决这些问题。完整盘点与 30 题见 [公司数据现状](26-company-data-and-agent-eval.md)。

两种方案比较：

| 方案 | 收益 | 代价 | 本项目判断 |
| --- | --- | --- | --- |
| wonder.db 中增加公司表 | 一库事务、外键与备份简单 | 公司投影与报告/会话共享文件、生命周期与迁移 | 仍可行，适合最少改动 |
| 独立 company.db | 公司查询层可独立重建、刷新、备份；职责易理解 | 需处理跨库来源校验、索引延迟与备份协调 | 更符合跨研究共享公司资料的目标 |
| 每家公司一个库 | 单公司文件独立 | 多公司对比、迁移、备份及连接管理复杂 | 当前没有必要 |

本地 wonder.db 当前约 81 MiB；source_page_fts 的 content/data 两张影子表合计约 65 MiB，是体积大头。拆公司库不会自动消除重复全文索引，也不能据此承诺查询提速或 token 降幅。共享全文索引另行评估。

## 2. 数据归谁管理

| 位置 | 职责 | 首版是否移动现有内容 |
| --- | --- | --- |
| data/wonder.db | 手动股票清单、Source 身份和获取事件、run_sources、正式研究、Agent 会话/Turn、Memo/记忆及审计 | 不移动；保持已有证据关系 |
| data/company.db | 从已登记归档解析出的版本化基本字段、财务/经营/营收构成事实、解析批次与覆盖信息 | 新建可重建投影；先回填现有资料 |
| data/stocks/... | 原始 JSON/PDF/文本与现有来源文件 | 原位置保留；不复制全文进公司事实库 |
| data/tmp/analysis/... | 选定数据的只读快照、SQL、受限计算代码与结果 | 沿用；记录来源及投影版本 |

**归档字节与 wonder.db 的来源登记是证据依据，company.db 是可重建查询层。** 不把 LLM 答案、Memo 推断或一段聊天自动写成财务事实；也不把平均值、CAGR 等每一种衍生指标预先做成专用存储或工具。

stocks.name 的四处缺失可由有来源的 profile 投影提供展示名，但不能把注册名称、上市证券简称与用户自定义名称混为一个字段。首版不搬迁 stocks 或 Source 主表。

## 3. 首版数据模型

首版已用三类业务表与 schema 版本记录，人工字段目录和覆盖统计从这些表查询产生。以下为总体设计；具体 v1 字段与尚未规范的元数据见实现文档，不把规范键等后续能力当作已实现。

| 表（拟定名） | 核心内容 |
| --- | --- |
| source_batches | source_id、ticker、provider、dataset、来源 SHA-256、解析器版本、完成状态、事实数量与诊断；一个已完成批次对应确定的来源版本与解析版本 |
| company_profile_facts | batch_id、原始字段键/名称、已确认的规范键、字段类型与值、可证实的生效时间、locator；公司名称/注册地/业务介绍/财年等 |
| financial_facts | batch_id、原始科目键/名称、可确认的规范键、原始数值文本、Decimal 值、币种、单位/倍率、期间标签及起止、期间类型、会计范围/准则、业务/地区等维度、披露时间、locator |

获取时间来自 Source，不能拿它代替披露时间或基本信息的生效时间。缺失元数据保留 unknown/null。财务年度、单季度、累计季度和时点数区分；美光的 FY 不自动换成公历年度。

历史时点还需要核对数值版本：今天取得的旧年度数据可能已经重述，不能仅凭原报告披露日期就声称这些数值当时已知。缺少对应历史版本及可用时间证据时，明确无法满足严格历史口径。

保留原始文本与可计算数值；未知倍率、百分数表示或币种的事实不能直接混算。JSON 业务维度仅承载来源实际提供的维度；不凭模型猜出云业务成本、归母范围或季度拆分。

相同科目在不同来源、重述或抓取版本下可以并存，不能用 ticker+年份+科目唯一键覆盖历史。批次内按源位置/维度去重；查询时再明确选来源与版本。不同 source_id 即使内容哈希相同，仍保留各自获取事件，必要时只复用解析工作。

确定性解析器按 provider/dataset 的真实结构覆盖 profile、statements、operational_efficiency、revenue_breakdown。规范字段映射只解决同义科目，不写死问答公式。无法识别的结构报告解析缺口，不能误标“公司未披露”。

## 4. 采集、索引与故障恢复

普通 Python 服务执行下列顺序，模型不直接写任一数据库：

```mermaid
flowchart LR
    A[已有归档或获准的富途补取] --> B[保存原始文件并校验哈希]
    B --> C[wonder.db 登记 Source]
    C --> D[确定性解析与字段校验]
    D --> E[company.db 事务提交完整批次]
    E --> F[按范围导出只读查询快照]
    F --> G[Agent SQL 或受限 Python 计算]
    G --> H[结果与原始来源引用]
```

原始文件和 Source 先落定，再投影 company.db；单库事务保证一个批次不会只露出半份事实。解析失败时保留可定位的失败诊断，不能对外声称事实索引成功。重试以 source_id+哈希+解析器版本幂等判断；启动/显式重建时比较已登记来源与已完成批次，补齐中断后的未索引来源。无需引入消息队列、通用事件重放或分布式事务。

company.db 对 wonder.db 的 source_id 无法使用跨库外键，需由程序验证身份、ticker、哈希与定位；这是 SQLite 的明确限制。[SQLite 外键文档](https://www.sqlite.org/foreignkeys.html)

不依赖 ATTACH 同时写两库来保证整个流程成功。SQLite 对附加数据库的跨库原子提交有条件限制，特别是 WAL 模式；本方案直接允许可恢复的索引延迟。[SQLite ATTACH 文档](https://www.sqlite.org/lang_attach.html)

首版沿用单机写锁和普通函数，不新增 ORM、仓储接口、依赖注入或后台调度。手动刷新和问答时按需刷新即可。解析器升级先生成新批次，验证完成再用于新查询，旧研究与旧计算产物保持原来源版本。

## 5. Agent 如何使用

1. 先查询实际字段目录与覆盖：知道有哪些指标、期间、单位、来源及缺口，返回有界摘要，不把全部公司财务塞入提示词。
2. 选择数据范围：普通当前公司问答可显式采用 company_latest；正式研究继续 run_sources；历史时点采用可证明截至 as_of 已披露的数据。company_latest 已在 B 实现，context=sources 仍不具备此语义。
3. 缺原始字段/期间或确实需要更新时，经现有网络权限调用富途只读接口；先补原始数据再入索引。区分未采集、解析失败、接口不覆盖与未披露。只缺平均值等衍生结果时直接计算，不重复请求数据。
4. SQL 仍运行于当前公司和本次范围的隔离快照；受限 Python 处理 SQL 不方便表达的简单计算。生成的代码不能直接读 company.db/wonder.db、网络、文件或环境变量。
5. 最终数值结论关联真实计算记录和原始输入引用；跨 Turn 复用时生成本 Turn 的证据回执，不因共享数据库跳过引用校验。

共享数据的“可检索”与“可引用”分开：候选可以来自公司已登记资料，但本次使用前仍需权限、ticker、来源哈希、时间范围与可用状态校验。失败来源和已标记撤回的来源不能被最新视图静默选中。具体来源失效状态沿用现有模型；若现有模型不足，实施时明确补充，不假装已有撤回机制。

新上下文应显式命名并版本化，不能悄悄把旧 latest_completed_report/latest_run 的含义换掉。旧问题重试、已完成正式报告、已保存 Memo 和计算快照不自动换用今天的新数据。

新鲜度按资料类型制定：年度报表关注最新已报告期间与修订，基本资料关注获取时间和用户要求，不能靠统一“一天过期”定时全量抓取。当前接口不支持的历史/季度/细分指标仍需报告真实缺口，建库不增加数据供应商的覆盖。

## 6. 备份与清理

A 阶段已为现有 backup 增加可选 company.db 快照与 manifest，沿用同一项目写锁；无公司库时兼容旧项目。B 已按分析状态收录计算快照、SQL、函数与结果，并用虚构资料完成恢复演练；完整主项目恢复尚未执行。目标是两库、原始资料、被引用计算产物、数据库/解析器版本与哈希都纳入备份并标明遗漏。SQLite backup API 提供单库快照，不能把先后两次备份说成天然的两库一致快照。[SQLite Backup API](https://www.sqlite.org/backup.html)

恢复后验证来源引用与哈希，必要时从原始归档重建 company.db。只删除公司投影不应损坏正式研究证据；删除原始文件则必须先检查正式报告、Memo 和计算引用。先做清理预览和恢复演练，再考虑回收历史版本。
